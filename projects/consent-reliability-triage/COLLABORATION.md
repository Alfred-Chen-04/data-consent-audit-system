# 多 Agent 协作与项目运行方案

> 版本：v1.0｜日期：2026-09-14｜适用项目：Consent Reliability Triage
> 当前安排：一个总控对话、一个工作包执行角色、一个按检查点启动的独立审查角色。
> 本文件规定协作方式；不表示已经创建助手、启动自动监控或完成独立审查。

## 1. 目的与总体架构

用明确分工、可追溯文件和独立检查，降低数据转换错误、共同假设和跨对话信息丢失的风险。项目仍以 DS / Analytics 和证据支持决策为主，沿用 Charter 的 46 小时核心计划、4 小时缓冲与 50 小时上限。

```text
项目负责人：研究方向、重要取舍、最终验收
                    │
总控对话：范围、进度、跨工作包决策、交接
                    │
工作包执行 agent ──提交固定版本──→ 独立审查 agent
       ↑                            │
       └────问题、证据、复核结果─────┘
                    │
        通过检查点、记录限制、交接下一工作包

共同依据：Charter + 决策日志 + 数据字典 + 原始证据 + 可复现产物
```

窗口只是操作界面；chat／任务保存各自的对话上下文；agent 是承担任务的执行者。多开窗口不代表协作，也不保证信息同步。新对话必须主动读取项目文件；重要结论不能只留在聊天中。

内部子 agent 只有在当前环境提供工具时才可使用。否则使用单独的审查 chat。不得把执行者自查标记为独立审查，或声称没有实际运行过的助手已经参与。

## 2. 谁负责什么

| 角色 | 主要责任 | 可以自行决定 | 必须交付／边界 |
|---|---|---|---|
| 项目负责人（用户） | 研究目标、学习目标、重要方法取舍、阶段验收 | 接受明确限制、调整范围或预算 | 能解释关键 SQL、指标与证据；不承担日常复制结果或逐行检查全部数据 |
| 总控 agent／当前总控对话 | 维护整体范围、依赖关系、状态与跨工作包决定；协调冲突 | 已授权范围内的文档整理、交接和任务拆分 | 根据实际文件报告进度；不假设自动监控其他 chat；不代替独立审查 |
| 工作包执行 agent | 检查输入、实现处理流程、运行检查、EDA、解释结果、处理审查意见 | 可逆的实现细节、查询与文件组织 | 提交代码、数据来源、检查结果、结论和限制；不能自己宣布独立审查通过 |
| 独立审查 agent | 从原始证据复核转换、口径和推断；复核重要修正 | 只读核查、在隔离输出目录重建、提出证据支持的反对意见 | 提交带证据的问题和覆盖范围；不直接改被审查的实现或报告 |
| 可选专题助手 | 有需要时核对规则定义、历史版本或特定方法 | 委派范围内的研究与独立输出 | 不直接合并主产物；执行 agent 整合，独立审查者仍检查关键判断 |

默认仅执行角色和审查角色承担工作包实务；总控按交接节点介入。角色可以在同一应用窗口中切换，不要求不同模型。不同模型也可能共享偏差，多数票不构成证据。

常规修正由执行 agent 处理，不逐项要求用户确认。改变研究问题、替换 baseline、扩大总工时、降低验收标准或影响后续评价有效性的取舍，由负责人决定并写入决策日志。公开发布、向维护者发消息或提交 issue／PR 需要对应授权；协作方案本身不构成该授权。

## 3. 文件与信息架构

当前有效项目根目录是 `projects/consent-reliability-triage/`。工作包执行以该目录下的 Charter 为准；工作区根目录的早期方向探索文档保留为历史背景。

| 文件／目录 | 内容与维护责任 |
|---|---|
| `README.md` | 项目导航与简要状态；总控维护 |
| `PROJECT_CHARTER.md` | 研究目标、范围、预算和证据边界；重要变更经负责人决定 |
| `WORKSTREAMS.md` | 工作包状态唯一主表；执行者交接时更新，总控核对 |
| `DECISION_LOG.md` | 会影响后续工作的决定、原因、影响及重开条件 |
| `COLLABORATION.md` | 本协作方案；变更留日期和理由 |
| `docs/WORK_PACKAGE_XX_RECORD.md` | 当前进度、已确认结论、产物、复现方式和下一步；执行者维护 |
| `docs/data_dictionary.md` | 字段语义、粒度、适用性和禁用解释；执行者维护并接受审查 |
| `evidence/sources/` | 已保存原始来源与 manifest；作为 raw 层，保持原始内容 |
| `scripts/`、`sql/` | 重建、清洗、质量检查和分析逻辑；执行者维护 |
| `data/cleaned/`、`data/analytical/` | 工作包 02 按实际实现建立的派生层，可从 raw 重建 |
| `analysis/` | EDA 结果、图表和候选问题；执行者维护 |
| `reviews/WPXX/` | 固定版本的审查报告、执行方回复和复核结论 |

以上派生数据及审查目录是约定，尚未创建的目录不代表已有产物。不为形式完整预先建立生产仓库、消息队列、服务或 dashboard。

当前 baseline 固定为 `evidence/sources/coverage_c2e9fcd6c22a.json`，来源身份和哈希以 `evidence/sources/manifest.json` 为依据。该文件的 205 个 rule key 和 433 条 rule × region 记录是对账控制值。工作包 02 应核验并登记实际 SHA-256；不能用文件名代替完整版本核验。

历史快照单独标记 snapshot ID，仅在可比性检查后使用。后续上游更新另开版本，不替换本轮 baseline。上游提交日期、下载日期和实际采集日期分别记录，未知采集日期保持未知。

若文档冲突，先核对用户最新明确决定和 `DECISION_LOG.md`，再修订相关文档；不要仅凭文档修改时间推断事实。无法从证据消除的冲突列入待决问题，不静默选一个版本。

## 4. 数据流与表结构原则

```text
raw：固定来源 + manifest
   ↓ 保留来源指针、字段存在性、转换规则
cleaned：统一类型、展开嵌套、记录质量问题
   ↓ 明确粒度与 JOIN，运行对账检查
analytical：可查询事实表／特征基础表
   ↓ SQL／分析脚本
EDA：描述性现象与候选问题
   ↓ 独立审查与交接
工作包 03：定义指标、设计排序与简单基线
```

初步表约定用于指导实现，最终字段和主键由工作包 02 依据实际 JSON 确定并记录：

| 对象 | 建议粒度 | 关键约束 |
|---|---|---|
| 快照元数据 | snapshot | 来源、hash、日期类型、baseline 标记 |
| coverage 事实 | snapshot × rule key × region | 保留计数原值；唯一键检查；缺失不自动补零 |
| 网站示例 | snapshot × rule key × region × 来源字段 × 数组位置 | 保留原 URL、示例类别和位置；同一 URL 可出现在不同类别 |
| 规则元数据／分类 | 明确版本中的 rule key | 分类附来源、理由和置信说明；跨版本映射需证据 |
| 候选特征基础 | 工作包 02 明确并记录的候选粒度 | 来源行可追溯；工作包 03 才确定评分及排序 |
| 逐次核查事实 | run_id，对应网站、环境和时间 | 与 coverage 聚合事实分开；防止连接后重复计数 |

网站示例表只能支持“已提供示例”的查询。`sites` 是数量，不能展开为完整网站清单；示例条数也不应被要求与 `sites` 相等。跨规则、跨地区求和不能解释成去重网站总数。

分类最好分开记录规则类型和地区适用性，避免把“地区专用”与“平台／网站／启发式”当成互斥类别。只凭名称推测的分类明确标为初步；证据不足保留 unknown，不强行分类。

## 5. 工作包 02 的执行顺序与两个审查点

### G1：基础表与质量检查

执行 agent 核验 baseline，登记三层映射，建立数据字典、重建命令和基础表。完成自查后提交固定版本供审查。

独立审查者检查：

1. 原始文件身份与 205／433 对账值是否一致；发现差异先解释，不能修改输入以凑数。
2. 数组展开、类型转换是否丢行；JSON 重复键是否被解析器静默覆盖；表主键和 JOIN 是否重复放大计数。
3. 缺失字段、null、空数组、显式零是否区分；异常值是否保留并报告。
4. 网站示例类别是否保留，是否被错误当成完整集合；URL 规范化是否改变含义。
5. `errors`、`selfTestFailures` 是否被错误相加；`unsuccessfulSites` 是否未经解释进入指标。
6. 独立重建是否成功；关键计数是否可直接从 raw 对照，而非只重跑同一段实现。

G1 通过后开展依赖这些表的正式 EDA；不受问题影响的文档和来源核对可继续。G1 问题影响哪些表、查询和数字必须写清。

### G2：EDA 与结论边界

执行 agent 输出字段分布、地区差异、规则分类、历史可比性和 3–5 个候选问题；若证据不足以支持该数量，说明缺口，不凑结论。

独立审查者检查：

1. 每个主要数字能否追到来源、查询和版本；描述是否写明分析单位。
2. 地区差异是否可能来自规则集合、站点集合或执行条件差异。
3. 异常集中和历史持续信号是否被误写成真实故障、同一网站复发或因果关系。
4. 规则分类是否有版本匹配的定义依据；未知和低置信分类是否可见。
5. 历史比较是否记录字段、自测逻辑、规则映射和运行条件的可比性；不满足条件时是否限制结论。
6. 是否提前形成正式排名、优化权重或利用 Bandcamp 开发结果声称独立评价。
7. 候选问题是否包含观察、可能解释、其他解释、缺失证据和决策意义。

未解释的 `unsuccessfulSites` 或不可比历史可以作为明确限制交接，不要求无限追查；相关推断必须撤下或收窄。工作包 02 不冻结最终评分，也不估计总体 recall／误报率。

## 6. 如何提交、审查与关闭问题

执行者提交审查时记录：工作包、检查点、输入 hash、被审查文件清单、代码版本或文件 hash、重建命令、检查结果、已知限制和输出位置。使用 Git 时记录 commit 及未提交改动；没有 Git 时记录文件 SHA-256。只记录 commit 而忽略未提交内容不能确定审查版本。

审查期间不修改该批关键输入和实现；必要修正形成下一版本并通知审查者。审查者若要重建，输出到独立临时目录，不覆盖主库或执行方产物。

每个问题使用稳定 ID，例如 `WP02-G1-001`，至少包含：

| 字段 | 要求 |
|---|---|
| 级别 | 必须修正／需要补证据／可选改进 |
| 位置与版本 | 文件、查询或结论，以及被审查版本 |
| 证据 | 观察、预期、实际结果；适用时附复现命令 |
| 影响 | 哪张表、哪些结论或下游决定受影响 |
| 建议 | 最小修正、补证据或缩小结论的方法 |
| 执行方回复 | 接受并修正／附证据反驳／建议保留为限制 |
| 状态 | 待处理／待复核／已关闭／已接受限制 |
| 复核结果 | 复核者、日期、新版本与依据 |

审查结论使用：通过、带明确限制通过、未通过。发现的问题数量不作为绩效；没有发现问题时仍说明查了什么、没查什么及残余风险。

执行 agent 不能自行关闭自己的必须修正项。审查者复核后关闭；有争议时双方各给证据。事实错误通过检查解决；方法偏好通过数据影响和敏感性讨论解决；涉及范围或验收标准的剩余分歧交负责人决定，不以投票裁决。

关键计数错误、不可重建、来源不明或影响核心结论的未解决问题阻止相关检查点通过。非核心证据缺口可通过撤回相关结论、标注限制并登记处理决定后继续。不得把未通过改写为“已完成”。

审查通过后的实质性改动需复核受影响部分；纯文字排版不要求全量重审。默认一轮审查和一次针对修正的复核；若问题仍在则保持未通过，并定位原因或缩减无依据的结论，不无限新增泛泛评论。

## 7. 其他工作包如何沿用

| 工作包 | 独立审查重点 |
|---|---|
| 01 | 当前按既有记录视为已完成；未做过的独立审查不追记成已完成。其输入假设在 WP02 G1 核对 |
| 02 | G1 数据忠实性；G2 描述和推断边界 |
| 03 | 分母、可比组、缺失策略、权重假设、简单基线、公平预算、开发样本泄漏；核查前冻结方案 |
| 04 | protocol 执行、原始日志、环境真实性、未决保留、运行与候选计数；基础核查与额外深查分开 |
| 05 | 比较是否公平、建议是否由证据支持、结论是否外推、是否把建议误写为实际效果 |
| 06 | 从原始输入复现、展示与结果同源、限制可见、发布材料与授权范围 |

审查工时纳入各工作包现有预算，记录负责人检查时间、agent／脚本运行时间和等待时间，避免混算。WP02 的 9 小时内优先预留约 1–1.5 小时负责人审阅与讨论检查点，这是安排建议，不是已发生工时。超出预算时先减少可选图表、分类细度或历史深度；影响核心范围时登记并由负责人决定。

只在两个子任务输入稳定、输出独立且预期节省时间时增加专题助手。共享数据库写入、表结构设计与依赖该结构的分析按顺序完成。同一文件同一时刻只有一个写入者；专题助手交到自己的目录，执行者检查后整合。

## 8. 实际开 chat 的方式

1. 保留当前对话作为总控；不用额外开应用窗口。
2. 在同一项目目录新建“工作包 02｜执行”；先读取共享文档。
3. 到 G1 时再启动“工作包 02｜独立审查”，或使用实际可用的内部子 agent。
4. 审查者保存报告，执行者读取并处理，审查者复核；G2 可继续使用同一审查对话。
5. 完成后执行者更新工作包交接和状态，总控据文件验收衔接。

本次只建立制度和文档，不自动创建新 chat。后续如要求创建任务，可使用应用提供的任务工具。没有消息工具时，用户只需在目标对话指示读取指定交接或审查文件，不必搬运整段历史。

### 执行对话启动指令

> 在 `projects/consent-reliability-triage/` 执行工作包 02。先读 README、Charter、WORKSTREAMS、COLLABORATION、DECISION_LOG、WP02 说明以及 WP01 交接、来源清单和数据字典。核验固定 baseline 的 manifest 与文件 hash，保留 raw／cleaned／analytical 三层。按 G1 建表和质量检查，再按 G2 做 EDA，不做正式排名。维护 WP02 过程记录，在每个检查点提交可复现的固定版本审查包；如未实际获得独立审查，明确记录待审。常规实现自行推进，关键范围变更写明影响。不要把示例网站当完整网站集合。

### 独立审查启动指令

> 独立审查工作包 02 的指定检查点。先读项目边界、协作方案、原始来源、数据字典及审查版本清单，再检查实现和报告。不要只依据执行方总结。核查数据转换、计数、JOIN、字段语义、分类依据和推断边界。需要运行时使用隔离输出。将报告保存到 reviews/WP02/，每个问题附位置、证据、影响和建议；报告覆盖范围和未检查项，不凑问题。不要直接修改被审查文件。收到修正后对实际新版本复核并记录关闭依据。

## 9. 每次暂停与工作包交接

暂停不等于完成。执行者在 `docs/WORK_PACKAGE_XX_RECORD.md` 留下：

```text
更新时间与当前工作包／检查点：
状态：未开始／进行中／受阻／已完成
已完成及对应产物：
输入版本、代码／输出版本：
重建命令、运行结果及未运行检查：
重要决定（链接 DECISION_LOG）：
审查报告、未关闭问题及接受的限制：
实际工时与剩余估计（未知则标未知）：
下一步可执行动作及依赖：
需要负责人决定的事项（无则写无）：
```

工作包完成时，除本包原有完成标准，还需有实际审查记录、关键问题处理结果、可用产物路径和下一包输入。`WORKSTREAMS.md` 仍只使用四种状态，审查阶段在交接文件单独记录，避免出现两套互相冲突的进度。
