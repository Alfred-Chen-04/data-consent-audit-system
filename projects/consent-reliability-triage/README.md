# Consent Reliability Triage

这是 data-consent-audit-system 仓库中的一个独立后续项目，用于在 10 周、30–50 小时内，训练以 Data Science / Analytics 为主体、以业务决策为落点的 consent reliability 分析能力。当前处于计划阶段，尚无已确认的问题或收益。

项目核心流程是：

~~~
公开异常 → 候选调查顺序 → 核查与解释 → 初步建议 → 评价依据 → 最终建议与证据
~~~

当前主要计划见 [PROJECT_CHARTER.md](PROJECT_CHARTER.md)（v0.4，2026-09-12）。

## 项目目标

帮助开源 consent 工具维护者回答：有限调查资源下，哪些异常值得先核查？核查后应该做什么，依据是什么？我们的筛选是否比简单做法更有帮助？

AutoConsent 是首个案例。先核实公开数据与少量运行证据能否支持分析，再形成可复现的调查队列和维护建议；不假设 DuckDuckGo 缺少内部分析或已经有采用意愿。

## 项目边界

- 研究对象是 AutoConsent 的公开运行与维护场景，不是企业内部合规审计。
- 项目不把网站直接判定为违法，也不承诺真实商业 ROI。
- SQL 和轻量本地分析数据层用于真实的数据连接与历史比较，不搭建生产级仓库。
- 当前未复现不等于误报；未决结果和“暂不建议修复”可以是有价值的结论。
- 默认评价筛选与建议依据；只有实际执行了工具改动，才另外评价工具是否改善。
- 真实用户 A/B test 不在范围内；小型工具实验须通过证据、设计与工时闸门，不强制做代码修复。
- 最终用版本化结果生成最小静态开源展示页，不做实时监测平台。

## 执行闸门

前两周先检查数据、样本映射与最小试跑，再确定指标和核查范围。核心计划 42 小时，缓冲与可选增强共 8 小时，50 小时封顶。比较筛选方法时预先固定基线和预算，不能只核查自己的首选就宣布更好。

## 仓库关系

仓库根目录中原有的 Dynamic Consent Interface Audit System 项目保持不变。本文件夹是后续独立的 Consent Reliability Triage 项目，不覆盖原有研究、数据或代码。
