# Consent Reliability Triage

这是 data-consent-audit-system 仓库中的一个独立后续项目，用于在 10 周、30–50 小时内，训练以 Data Science / Analytics 为主体、以业务决策为落点的 consent reliability 分析能力。工作包 01 已完成，工作包 02 尚未开始；已有最小试跑证据，尚无已确认的 bug 或收益。

项目核心流程是：

~~~
公开异常 → 候选调查顺序 → 核查与解释 → 初步建议 → 评价依据 → 最终建议与证据
~~~

当前主要计划见 [PROJECT_CHARTER.md](PROJECT_CHARTER.md)（v0.5，2026-09-12）。

实际执行从 [WORKSTREAMS.md](WORKSTREAMS.md) 开始。项目已拆成 6 个可以分别在新对话中推进的工作包；每个工作包都包含输入、步骤、产出、完成标准和可直接复制的新对话开场提示。

协作方式见 [COLLABORATION.md](COLLABORATION.md)：一个总控对话、一个工作包执行角色、一个按检查点启动的独立审查角色。该文档包含责任划分、数据与文件架构、审查闭环、验收要求及可复制的启动指令。当前仅完成协作方案，尚未启动审查任务。

## 项目目标

模拟分析型 DS 为 PM／项目组提供数据支持的工作：从 messy data 发现线索、建立指标与可复用排序方法，核查候选，再给出建议。具体回答：有限调查资源下，哪些异常值得先查？查完应该做什么？这套分析相比简单排序多提供了什么帮助？

AutoConsent 是首个案例。先核实公开数据与少量运行证据能否支持分析，再形成可复现的调查队列和维护建议；不假设 DuckDuckGo 缺少内部分析或已经有采用意愿。

## 五个阶段

1. 看清数据来源与口径，用 SQL 整理并连接分散的信息。
2. 从 EDA 中提炼指标，设计排序并检查不同标准对选择的影响。
3. 核查自定义排序的 Top 10–20 个候选：运行相关样本、查看记录，保留已复现、未复现与未决结果。
4. 根据证据形成面向 PM／维护者的建议，与同 K 的简单排序比较；基线额外候选也需核查并计入工时。
5. 以小型开源页面展示分析、证据和建议，同时提供可重新运行的 SQL、排序配置和方法说明。

## 项目边界

- 研究对象是 AutoConsent 的公开运行与维护场景，不是企业内部合规审计。
- 项目不把网站直接判定为违法，也不承诺真实商业 ROI。
- SQL 和轻量本地分析数据层用于真实的数据连接与历史比较，不搭建生产级仓库。
- 当前未复现不等于误报；未决结果和“暂不建议修复”可以是有价值的结论。
- 默认评价筛选与建议依据；只有实际执行了工具改动，才另外评价工具是否改善。
- 真实用户 A/B test 不在范围内；小型工具实验须通过证据、设计与工时闸门，不强制做代码修复。
- 最终用版本化结果生成最小静态开源展示页，不做实时监测平台。

## 执行闸门

前两周先检查数据、样本映射与最小试跑，再确定指标和核查范围。先按自定义 Top 10 规划，扩到 20 需实际工时支持。候选数、网站数和运行次数分别记录；同 K 基线的额外候选也计入工作量。核心计划 46 小时、缓冲 4 小时，50 小时封顶。

SQL 可以自然包含多表连接、去重、时间条件连接和窗口计算；具体用法服务于实际问题。A/B test 保持可选，优先完成指标解释、基础核查和有依据的决策评价。比较筛选方法时预先固定基线和预算，不能只核查自己的首选就宣布更好。
