# Consent Reliability Triage：从公开运行数据到可执行维护决策

> 版本：v0.3 draft
> 日期：2026-09-11
> 状态：项目计划草案，等待讨论
> 预计周期：10 周
> 预计总投入：30–50 小时

## 1. 项目一句话

用 DuckDuckGo AutoConsent 的公开运行数据、历史记录和维护信息，识别值得优先调查的 consent automation 失败模式，验证这些候选问题是否真实且可复现，再为有限维护资源提出一项有证据的行动建议，并检查这套判断是否有效。

本项目不是“做一个排行榜”，也不是默认去修改某个网站。排序只是中间步骤。项目的核心是：

~~~
messy data → 候选问题 → verify 真伪 → 优先级决定 → 行动建议 → 回测或复查
~~~

## 2. 为什么这个问题值得研究

大型组织通常需要在多个网站、地区、设备、语言和第三方工具之间维护 consent 配置。真实业务困难往往不是缺少一个按钮，而是：

- 配置和网页行为经常变化；
- 不同地区的 consent 规则可能不同；
- 公开运行结果中会出现错误、失败和不一致；
- 维护团队不可能同时调查所有问题；
- 原始数据通常不能直接告诉团队“下一步最应该做什么”。

AutoConsent 提供了一个公开、可运行、可观察的窄场景。它可以作为 consent operations 中“故障筛选和维护资源分配”的案例，而不是整个企业 consent 管理的替代品。

## 3. 业务问题

面向的决策者是：

- 开源隐私工具维护者；
- consent/privacy operations 团队；
- 负责测试、监控和规则维护的产品或工程负责人。

他们要做的决定是：

> 如果下一轮只有有限的维护或测试时间，应该先调查哪一种 consent automation 失败？为什么？需要采取什么行动？

本项目希望把“公开数据分析”转化成一个维护决策：

- 哪类问题值得继续调查；
- 哪类问题只是一次性异常；
- 哪类问题需要增加测试；
- 哪类问题值得修复或提交公开 issue；
- 哪类问题应暂时记录为已知限制。

## 4. 研究问题

### 主研究问题

> 在 AutoConsent 的公开运行数据中，哪些失败模式经过 verify 后仍然被证明是重复、可复现、具有较大影响范围且值得优先处理？

### 次级问题

1. coverage 数据、历史版本和维护记录能否支持可信的候选问题筛选？
2. 初步排序中有多少候选问题经过 verify 后其实无法复现？
3. 哪些指标会稳定影响优先级，哪些指标会造成排序变化？
4. 一组小型、可复现的测试样本能否覆盖历史上反复出现的重要失败？
5. 分析结果能否转化为维护者可以执行的下一步行动？

## 5. 分析单位

本项目不把一个网站整体打分，也不把“网站是否合法”作为目标。

最小分析单位暂定为：

> rule/CMP × region × failure pattern

例如：

> 某类 CMP 的 opt-out 处理，在某一地区的多个网站上出现重复失败。

这里的“失败”是工具层面的操作失败，例如：

- 弹窗没有被识别；
- opt-out 操作没有完成；
- 选择结果无法验证；
- 某个地区或设备上的表现明显不稳定。

它不自动等于隐私违法，也不自动等于真实用户受到了同样程度的影响。

## 6. 项目方法

### 6.1 阶段一：候选问题筛选

使用公开的：

- AutoConsent coverage 数据；
- 历史 coverage snapshots；
- 规则和测试文件；
- GitHub issues、PRs、commits 和 releases；
- 必要的公开运行日志或截图。

先生成一张候选问题表。第一版不强行制作一个看似精确的黑箱分数，而是保留每个维度的可解释证据：

| 维度 | 要回答的问题 |
|---|---|
| 影响范围代理 | 涉及多少网站、地区或规则触发？ |
| 失败表现 | 错误或 self-test 失败是否在可比条件下发生？ |
| 重复性 | 是否在多个历史版本或公开记录中出现？ |
| 证据质量 | 是否有测试、示例网站、日志或 issue 支持？ |
| 可行动性 | 是否能定位到规则、测试、监控或责任方？ |
| 成本粗估 | 预计调查或维护成本是低、中还是高？ |

任何权重都必须写出理由，并做敏感性分析。权重不是“业务真理”，而是项目负责人公开声明的决策假设。

### 6.2 阶段二：Verify 候选问题

初步排序只代表“值得优先验证”，不代表问题已经被证明。

对前几个候选问题：

1. 选择少量代表性网站或测试样本；
2. 在固定条件下重复运行；
3. 记录结果、错误阶段、截图和运行环境；
4. 检查历史记录和公开维护信息；
5. 将候选分类为：
   - 已确认且可重复；
   - 只在特定条件下出现；
   - 无法复现，可能是假警报；
   - 已经被修复。

这里的目标不是大规模人工标注，而是对最终进入公开结论的少量 finding 做证据核验。

### 6.3 阶段三：形成行动建议

只有通过 verify 的候选问题才能进入最终决策。

根据问题的影响、证据质量、可复现性和成本，选择一项行动：

- 增加某类回归测试；
- 建立一组小型长期 benchmark；
- 提交带有复现步骤的公开 issue；
- 建议维护者优先修改某类规则；
- 增加某种失败监控；
- 如果证据不足，明确建议暂不投入。

项目必须给出“为什么是这个行动，而不是其他行动”的解释。

### 6.4 阶段四：验证行动是否有效

根据行动类型选择相应的验证方式：

| 行动 | 可测量结果 |
|---|---|
| 规则或配置发生小范围变化 | 目标样本的成功率、错误率或可验证性变化 |
| 增加 benchmark/test set | 对历史失败的覆盖率、发现率和排序稳定性 |
| 提交 issue/evidence package | 是否具备完整复现证据，维护者是否反馈（stretch） |
| 暂不投入 | 是否能说明候选问题无法稳定复现或影响范围过窄 |

项目不把“上游一定 merge”或“商业网站一定整改”作为硬性成功条件。

### 6.5 Measurement 与 A/B test 的边界

本项目默认不做真实用户 A/B test。我们没有商业网站的流量控制权，也不能随机分配真实用户看到的 consent 版本。

需要区分三种验证：

1. **Verify candidate：**判断初步发现是不是真问题；
2. **Controlled comparison：**在相同样本、地区、设备和运行条件下比较当前方案与候选方案；
3. **Follow-up measurement：**检查行动之后目标指标是否发生变化。

如果可以控制同一批测试样本，可以固定运行条件、随机化运行顺序、重复执行，并比较：

- 自动处理成功率；
- 错误率和超时率；
- self-test 通过率；
- 完成时间或重试次数（只有实际记录了这些字段才使用）。

如果最终行动会改变可执行行为，实验设计应明确：

- **Control：**当前版本的规则或运行方案；
- **Treatment：**预先定义的一项小范围变化；
- **实验单位：**网站 × 地区 × 设备的一次运行；
- **主要 estimand：**Treatment 相对于 Control 对目标结果的平均影响；
- **阻断与随机化：**在同一网站、地区和设备内配对，并随机化运行顺序；
- **不确定性：**报告差异的区间、重复运行结果和样本限制。

如果最终行动只是增加 benchmark、监控或公开 issue，则没有可比较的 Treatment，不做强行的 A/B 叙述；这时应评估历史失败覆盖率、误报比例或证据完整性。

这种设计应称为 controlled comparison 或 benchmark experiment，不应包装成用户级 A/B test。

A/B test 是估计因果影响的一种实验设计，但 A/B test 不等于完整的因果推断。因果推断还需要明确反事实、处理混杂因素、定义 estimand，并说明外推边界。用户级 A/B test 只有在未来获得真实流量、随机分组和明确业务指标时才适用。它不是为了简历而强行加入的关键词。

不同阶段的 measurement 也不同：

| 阶段 | 主要测量 |
|---|---|
| 候选筛选 | Top-K 候选的后续确认率、排序稳定性 |
| Verify | 重复运行的一致性、可复现率、误报比例 |
| 测试或规则行动 | 成功率、失败率、可验证性或完成时间变化 |
| Benchmark 行动 | 对历史失败的覆盖率和发现率 |
| 外部反馈 | 证据是否被理解、是否有人愿意使用或跟进 |

## 7. DS 技术要求

项目主体应体现以下 Data Science / Analytics 能力：

### 7.1 每个阶段使用的 skills

| 阶段 | 主要工作 | DS / Analytics skills | PM / 业务 skills | 主要证据 |
|---|---|---|---|---|
| 定义问题 | 明确谁要做什么决定 | problem framing、metric definition、假设拆解 | 识别决策者、目标和约束 | decision question |
| 理解数据 | 追踪数据如何生成 | data lineage、schema review、data quality、provenance | 判断数据能否支持业务结论 | source inventory、data dictionary |
| 生成候选 | 从运行记录中找信号 | EDA、aggregation、rate/denominator、segmentation | 定义影响范围的合理代理 | candidate findings table |
| Verify | 判断候选是否为真 | repeated measurement、experiment design、error analysis、uncertainty | 设定证据门槛，避免误报 | verification evidence pack |
| 优先级 | 比较多个已验证问题 | multi-criteria analysis、sensitivity analysis、backtesting | trade-off、资源分配、明确 recommendation | priority matrix |
| 行动 | 将 finding 映射到下一步 | action-to-metric mapping、evaluation design | 维护任务、测试计划、issue 或反馈 | decision memo |
| 复查 | 测量行动之后的变化 | before/after、controlled comparison、historical recall | 判断是否继续、扩大、暂停或转向 | evaluation result |
| 公开交付 | 让别人理解并复用 | reproducibility、documentation、result communication | audience design、责任披露、边界管理 | open-source site、case brief |

### 7.2 SQL 与本地 analytical warehouse

为了补充市场上常见的 SQL 和数据仓库能力，项目加入一个轻量级本地分析存储层：

- 使用 DuckDB 或 SQLite，不搭建云端生产数据仓库；
- 将原始 coverage、历史快照、GitHub 事件、运行结果和 finding 记录分层保存；
- 用 SQL 完成核心聚合、连接、去重、时间比较和候选生成；
- 保留 raw、cleaned 和 analytical tables 的关系；
- 为关键表增加基本的 schema、唯一性和完整性检查；
- 让网站和 notebook 使用同一份可重建的分析表。

这部分展示的是数据建模、ETL/ELT、SQL 查询和可复现分析存储，不是分布式数据工程。

### 7.3 Controlled experiment 与因果推断

项目可以加入一个范围很窄的 A/B-style controlled experiment，但它研究的是工具行为，不是用户转化：

1. 先固定一批已 verify 的网站、地区和设备；
2. 把当前规则作为 Control；
3. 选择一项明确的候选变化作为 Treatment；
4. 在每个测试单位内配对和随机化运行顺序；
5. 重复运行并估计成功率、错误率或完成时间的差异；
6. 报告置信区间、样本量、运行失败和可能的混杂因素。

结果只能支持类似“在选定样本和运行条件下，Treatment 的工具成功率高于 Control”这样的结论，不能外推为所有网站、真实用户或商业 KPI 的因果效果。

如果无法找到安全、可解释的 Treatment，则不强行做实验，改用历史回测和重复测量，并明确说明因果推断缺失。

### 7.4 数据理解与工程

- 识别不同数据源的生成过程；
- 建立 data dictionary 和 provenance；
- 读取和合并 coverage JSON、历史快照、测试元数据和 issue/PR；
- 处理 schema 变化、缺失字段、重复记录和不可比的分母；
- 保留原始数据与清洗后数据的关系。

### 7.5 分析与建模

- 选择合理的分析粒度；
- 区分数量、比例和分母；
- 进行 failure-mode segmentation；
- 分析时间趋势、重复出现和修复后的变化；
- 识别误报、选择偏差和可比性问题；
- 构建透明的多指标优先级框架；
- 做敏感性分析和不确定性说明；
- 用历史数据进行 backtesting。

### 7.6 决策与评估

- 把候选问题转成可验证假设；
- 设计低成本、可复现的验证方案；
- 将 finding 映射到具体 action；
- 为 action 定义验收指标；
- 清楚说明 observation、interpretation 和 claim 的边界。

AI 可以辅助文本提取、初步分类、代码生成和假设挑战，但不能替代证据核验，也不能自动宣布某个网站违法。

### 7.7 能获得、部分获得和无法获得的能力

#### 本项目可以较强地展示

- 从模糊问题出发建立分析框架；
- 处理分散、不完整、带噪声的公开数据；
- 设计指标、分析粒度和数据质量检查；
- 识别候选信号并验证真假；
- 使用敏感性分析和历史回测支持决策；
- 把数据分析转换成资源优先级和行动建议；
- 用可复现代码、证据链和清楚的限制进行沟通。

这些能力在 Data Analyst、Product Analyst、Decision Science、Privacy Analytics 和 Data Governance 等岗位中具有较强通用性。

#### 本项目计划重点补充

- **SQL / 数据仓库：**使用 DuckDB 或 SQLite 作为本地 analytical warehouse，并用 SQL 完成核心转换和聚合；
- **统计推断：**对重复运行结果报告区间和不确定性，而不是只报告一个比例；
- **实验设计与因果推断：**在存在可执行 Treatment 时完成配对、随机化的 controlled comparison；否则诚实记录不能进行因果估计；
- **stakeholder feedback：**邀请开源维护者或隐私从业者评价 decision memo 的可用性。

#### 本项目不能替代真实 internship

- 真实用户流量 A/B test，以及具有商业 KPI 的完整因果推断；
- 生产级数据仓库、实时 pipeline 和大规模云基础设施；
- 真实收入、转化、客户流失或 ROI；
- 与法务、营销、工程和产品团队的长期协作；
- 真实组织是否采纳建议；
- 高级机器学习模型、模型部署和线上监控。

因此，面试时应说“完成了一次端到端的公开数据决策分析”，而不是声称做过生产级 DS 或证明了商业 ROI。

## 8. PM 与业务落点

PM 部分不负责把项目变成一个完整产品，而负责把分析结果落成一个明确决定：

1. 明确谁需要使用结果；
2. 明确他们要做什么资源分配决定；
3. 说明不同选项的 trade-off；
4. 给出推荐行动和验收标准；
5. 记录结果是 improved、unchanged、unresolved，还是无法判断。

最终业务产出应类似一份内部 decision memo：

> 建议维护团队优先处理问题 A，而不是问题 B。问题 A 在多个历史版本中重复出现，并在代表性样本中可以复现；问题 B 只在单个样本中出现且当前无法稳定复现。建议先投入一次测试/维护行动，并用指标 X、Y、Z 评估结果。

这类结论的商业价值主要体现为：

- 减少人工排查范围；
- 缩短从运行异常到维护决定的时间；
- 让测试和维护资源更集中；
- 提供可审查、可复现的决策依据；
- 降低因为 consent automation 不稳定而产生的维护不确定性。

本项目不能仅凭公开数据声称带来了具体收入、合规认证或真实用户数量的变化。若要增强业务真实性，可以在后期邀请一位开源维护者或隐私从业者对 decision memo 提供反馈。

### 8.1 开源网站作为最终交付

项目可以沉淀成一个轻量级、静态的开源网站。网站是分析方法和结果的产品化呈现，不是另一个 CMP 或实时扫描平台。

最小网站包含：

1. **Priority queue：**展示候选问题、verify 状态、影响范围代理、证据质量和推荐行动；
2. **Finding detail：**说明问题如何产生、使用了什么数据、如何复现、哪些结论仍不确定；
3. **Historical view：**展示不同版本和时间点的变化；
4. **Method and limitations：**解释指标、权重、measurement、A/B 边界和数据限制；
5. **Export：**生成 decision memo、issue 模板或 evidence package。

网站不应只显示“哪些地方有问题”，而应回答：

> 基于目前证据，下一步最值得做什么？为什么？如果做了，应该如何判断是否有效？

第一版不做实时后台、用户账号、持续全网扫描或企业私有数据 connector。可以使用静态生成、GitHub Pages 或同类方式，避免把时间花在产品基础设施上。

## 9. 最小可行范围

十周内只做一个小闭环：

- 一个主要问题族；
- 一个主要开源项目：AutoConsent；
- 一组有限的历史数据和公开维护记录；
- 最多 3 个优先候选进入深度 verify；
- 一个最终确认的问题；
- 3–5 个代表性样本；
- 一项行动建议；
- 一次回测或 follow-up 验证。

以下内容不属于第一版：

- 全网大规模审计；
- 给网站或公司做法律合规排名；
- 训练预测模型；
- 建立大规模人工标注集；
- 开发新的浏览器自动化平台；
- 构建实时 SaaS、带后端的企业 dashboard 或持续全网扫描服务；
- 做真实用户流量 A/B test；
- 证明上游一定采用建议。

允许的最终展示形式是基于版本化分析结果生成的轻量级静态开源网站。

## 11. 成功标准

项目完成不以数据量或图表数量衡量，而以以下结果衡量：

1. 能从公开原始数据重现主要分析结果；
2. 能清楚说明候选问题与已确认问题的区别；
3. 能证明至少一个候选经过 verify 后被确认、缩小或排除；
4. 能解释最终优先级不是由单一数字决定；
5. 能提出一项具体、可执行的维护或测试行动；
6. 能用回测、重复运行或 follow-up 说明行动是否有效；
7. 能清楚说明数据限制、外推边界和未解决问题；
8. 核心候选生成和聚合能够用 SQL 在本地 analytical warehouse 中重建；
9. 如果存在可执行 Treatment，能够报告工具层 effect estimate 和因果外推边界；如果不存在，能够解释为什么不能做因果估计；
10. 另一个读者能够根据网站和方法文档复现主要判断；
11. 最终成果能够作为 DS + privacy/product analytics 的面试案例。

## 12. 风险与转向条件

### 风险一：coverage 数据不包含足够的规则—网站关系

应对：先检查测试文件、示例列表和历史快照。如果无法形成可靠映射，不做“测试资源优化”，转向 issue/PR 失败模式分析。

### 风险二：候选问题无法复现

这不是项目失败。应如实记录为 false alarm 或 unresolved，并分析为什么初步数据会产生该候选。

### 风险三：项目逐渐变成代码修复

代码修改只能作为可选的验证手段。若需要大量工程工作，应回到数据分析、验证设计和决策建议。

### 风险四：没有外部组织采纳建议

项目应把“可复现 evidence package 和 decision memo”作为主要交付，外部 merge、部署或回应作为 stretch outcome。

### 第一个转向闸门

如果第 4 周仍然无法得到可比较、可追溯的数据，项目必须暂停 AutoConsent 的具体排序，改用公开 issue/PR 历史或另一个数据源，不允许继续靠假设扩展范围。

## 13. 预期最终交付

最小开源交付包括：

1. data_dictionary.md；
2. 可复现的数据提取和分析代码；
3. 候选问题与优先级表；
4. verify 证据包；
5. 一份面向维护者的 decision memo；
6. 一份消费者或非技术读者能理解的 case brief；
7. 一份回测或 follow-up 结果；
8. 一份方法论文档（METHOD.md）和可复用模板；
9. 一个基于分析结果生成的轻量级静态开源网站；
10. 一段诚实、可量化的简历描述。

### 方法论沉淀

最终沉淀的不是一套只适用于 AutoConsent 的打分公式，而是一套可迁移的 Evidence-to-Action workflow：

~~~
定义决策问题
→ 建立证据链
→ 生成候选
→ Verify 真伪
→ 透明地排优先级
→ 选择行动
→ 测量结果
→ 公开限制并允许复用
~~~

方法文档必须写清楚输入、分析单位、候选生成规则、verify protocol、优先级维度、action-to-metric mapping、转向条件和不确定性说明。

在只有一个案例时，应称为“经过案例验证的可复用决策框架”，不应声称已经证明对所有 consent 或隐私问题普遍有效。若时间允许，可以用第二个 failure pattern 做小型 transfer test，检查流程是否仍然适用。

推荐的最终案例名称：

> **Consent Reliability Triage：用公开运行证据识别并验证 AutoConsent 中最值得优先处理的失败模式**

## 14. 面试叙事模板

面试时应按以下顺序讲：

1. 业务背景：多网站、多地区的 consent automation 维护复杂，团队不能同时处理所有异常；
2. 决策问题：有限时间下，下一轮应该先调查什么；
3. 数据问题：公开数据分散、字段不完整、候选失败可能是假警报；
4. DS 方法：建立分析单位、清洗数据、设计指标、验证候选、做敏感性分析；
5. 行动：选择一个高置信度问题，提出测试、监控或维护建议；
6. 结果：用回测或复查说明建议是否有效；
7. 限制：没有企业内部流量和商业结果，因此只报告能够被公开证据支持的结论。

不要把项目说成已经替代企业内部审计，也不要把工具层失败直接说成法律违规。

## 15. 当前待讨论的问题

以下内容在本草案中暂不提前假设：

- 最终是否使用 AutoConsent 作为唯一数据源；
- 第一个问题族具体是哪一种失败；
- 是否需要实际修改一条规则；
- 是否向上游维护者发送 issue 或 PR；
- 是否增加少量 practitioner feedback；
- 最终以 benchmark、evidence package 还是两者共同作为主要行动产出。

这些决定应在第 1 周 feasibility check 和第 2 周数据审查后再确认。
