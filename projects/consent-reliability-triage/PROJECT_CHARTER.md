# Consent Reliability Triage：从公开运行数据到可执行维护决策

> 版本：v0.5（对齐 DS 角色与 Top 10–20 核查范围）
> 更新日期：2026-09-12
> 状态：方向已确认；具体样本、指标阈值和实验待可行性检查
> 预计周期：10 周
> 预计总投入：30–50 小时；基准计划 46 小时，缓冲 4 小时；按核查 Top 10 起步，扩至 20 需试跑工时支持

本文件是 `projects/consent-reliability-triage/` 的当前计划入口。根目录旧项目的审计维度和暑期技术方案继续适用于旧项目；本项目沿用证据可追溯原则，使用这里明确的分析单位和边界。当前只有计划文档，尚未完成数据可行性验证，也没有已确认 finding 或业务收益。

## 1. 项目一句话

以 DuckDuckGo AutoConsent 为案例，练习 Data Scientist 从 messy data 中发现线索、建立指标、核查判断，并为 PM／项目组提供有依据的决策建议：人工复查时间有限时，哪些异常值得先查，查完以后应该做什么？

项目负责人承担分析型 DS 的角色；开源工具的维护者或产品负责人是建议的潜在使用者。目前模拟这个协作场景，尚无实际项目组委托。最终交付包含可复现分析、可复用排序流程、行动建议和轻量级开源页面。

### 1.1 用大白话说，十周要做什么

1. 看清公开数据有什么、能回答什么，再用 SQL 和数据清洗整理起来。
2. 从数据里找重复异常和其他值得解释的现象，据此设计指标与排序方法，检查不同合理标准会不会改变选择。
3. 挑排名靠前的 10–20 个候选案例，实际运行相关样本、查看记录，为每个案例留下核查结果。具体计数和核查深度见 §6.2。
4. 根据证据建议补测试、进一步调查或暂缓；与简单按错误数量排序比较，解释我们的分析多提供了哪些信息，是否改变了下一步决定。
5. 把方法、证据和建议放到一个小型开源页面，并提供让别人重新运行这套流程的 SQL、配置和说明。

核心学习目标是能亲自解释“数据里发现了什么 → 为什么定义这个指标 → 核查改变了什么判断 → PM 可以据此做什么”。A/B test 是条件允许时的增强；SQL 的深度通过实际分析问题来体现。

本项目不是“做一个排行榜”，也不是默认去修改某个网站。排序只是中间步骤。项目的核心是：

~~~
公开数据 → 候选调查顺序 → 核查与解释 → 初步行动建议
→ 评估建议依据或开展小型试点 → 最终建议 + 证据 + 适用范围
~~~

## 2. 为什么这个问题值得研究

大型组织通常需要在多个网站、地区、设备、语言和第三方工具之间维护 consent 配置。真实业务困难往往不是缺少一个按钮，而是：

- 配置和网页行为经常变化；
- 不同地区的 consent 规则可能不同；
- 公开运行结果中会出现错误、失败和不一致；
- 维护团队不可能同时调查所有问题；
- 原始数据通常不能直接告诉团队“下一步最应该做什么”。

AutoConsent 是用于自动处理弹窗的开源库，可在浏览器扩展或 Playwright 环境中运行，DuckDuckGo 浏览器应用使用了它。[官方说明](https://github.com/duckduckgo/autoconsent/blob/main/readme.md)

企业 consent 管理确有实际投入：例如服务商公布的案例记录了同意数据不一致导致营销活动暂停的情况。[Grant Thornton 案例](https://www.grantthornton.com/insights/case-studies/hospitality-and-restaurants/2026/enterprise-preference-center-boosts-privacy-compliance) 这支持领域需求，但不能证明 AutoConsent 维护者缺人、缺少内部排序机制，或愿意采用我们的工具。公开仓库没有展示的能力也可能在内部存在。

本项目的需求假设是：透明的调查队列和证据包可能降低维护者的核查负担。第一周检查公开工作流程和已有输出是否支持这一假设；没有直接反馈时，项目仍是独立决策支持原型，商业价值属于待验证假设。

## 3. 业务问题

第一版的建议面向 AutoConsent 或类似开源隐私工具的维护者、产品负责人；本项目模拟由 DS 为 PM／项目组提供数据支持的工作方式，不假设 AutoConsent 实际存在特定的 PM 岗位或组织结构。技术研究者可以复用方法；普通消费者是潜在的间接受益者。企业 consent/privacy operations 是技能迁移方向，不将企业内部配置与 AutoConsent 的自动操作故障混为一谈。

他们要做的决定是：

> 如果下一轮只有有限的维护或测试时间，应该先调查哪一种 consent automation 失败？为什么？需要采取什么行动？

本项目希望把“公开数据分析”转化成一个维护决策：

- 哪类问题值得继续调查；
- 哪类问题只是一次性异常；
- 哪类问题需要增加测试；
- 哪类问题值得修复或提交公开 issue；
- 哪类问题应暂时记录为已知限制。

## 4. 研究问题

### 主研究问题

> 在固定调查预算和明确的证据条件下，我们能否从 AutoConsent 公开异常中识别可行动的候选，并通过核查给出比仅看错误数量更有依据的维护建议？

### 次级问题

1. coverage 数据、历史版本和维护记录能否支持可信的候选问题筛选？
2. 核查后，哪些候选得到确认、排除，哪些仍无法判断？
3. 哪些指标会稳定影响优先级，哪些指标会造成排序变化？
4. 在数据允许时，新方法与简单排序在相同调查预算下有何差别？
5. 分析结果能否转化为维护者可以执行的下一步行动？

## 5. 分析单位

本项目不把一个网站整体打分，也不把“网站是否合法”作为目标。

必须区分三个粒度：

| 阶段 | 一条记录代表什么 | 用途 |
|---|---|---|
| 原始统计 | 快照 × rule × region | 找运行异常信号；CMP 与 rule 不一定一一对应 |
| 核查记录 | 网站 × 环境 × 时间 × 运行编号 | 保存具体观察、失败阶段与核查结论 |
| 决策候选 | 有证据支持的同类异常集合 | 推荐调查、增加证据、测试或维护；失败原因未知时明确标记未知 |

不能从聚合计数直接推断具体失败原因。相同规则在多个快照出错，也不一定是同一批网站反复发生同一个 bug。

例如：

> 某类 CMP 的 opt-out 处理，在某一地区的多个网站上出现重复失败。

这里的“失败”是工具层面的操作失败，例如：

- 弹窗没有被识别；
- opt-out 操作没有完成；
- 选择结果无法验证；
- 某个地区或设备上的表现明显不稳定。

它不自动等于隐私违法，也不自动等于真实用户受到了同样程度的影响。

### 5.1 已知数据条件与缺口

根据[官方 coverage 定义](https://github.com/duckduckgo/autoconsent/blob/main/data/Readme.md)：

| 已有字段 | 可以说明什么 | 使用限制 |
|---|---|---|
| sites | 该规则被检测到的网站数 | 不是用户数、完整 opt-out 尝试数或跨规则去重站点数 |
| errors | 处理规则时出错的网站数 | 不直接给出根因；不能与其他失败计数直接相加 |
| selfTestFailures | 有自测的规则在 opt-out 后自测未通过 | 自测可选；没有自测或计数为零不证明操作成功 |
| exampleSites / failingSites / errorSites | 每类最多 5 个示例 | 不是完整样本清单，不能据此声称完整覆盖率 |

因此不使用 `1 - errors / sites` 作为工具成功率，也不把 `selfTestFailures / sites` 当作自测执行失败率。只有确认实际执行次数和可比条件后才能定义相应分母。其他未解释字段先保留原值，不进入核心指标。

历史快照与 issue/PR 用于补充时间和上下文。需核对规则重命名、合并、自测变化、爬取条件及日期；提交日期不一定等于采集日期，不能补写未知日期。不存在完整历史运行日志时，不承诺得到逐网站历史真值。

## 6. 项目方法

### 6.1 阶段一：候选问题筛选

使用公开的：

- AutoConsent coverage 数据；
- 历史 coverage snapshots；
- 规则和测试文件；
- GitHub issues、PRs、commits 和 releases；
- 可获得的运行证据，以及本项目小规模核查产生的日志或截图。后者需要自己运行，不假设已存在于公开数据中。

先生成一张候选问题表。第一版不强行制作一个看似精确的黑箱分数，而是保留每个维度的可解释证据：

| 维度 | 要回答的问题 |
|---|---|
| 影响范围代理 | 涉及多少网站、地区或规则触发？ |
| 异常表现 | 计数口径和自测能力是否可比？数据缺口有多大？ |
| 重复性 | 是否在多个历史版本或公开记录中出现？ |
| 证据质量 | 是否有测试、示例网站、日志或 issue 支持？ |
| 可行动性 | 是否能定位到规则、测试、监控或责任方？ |
| 成本粗估 | 本项目核查成本是低、中还是高？未知修复成本单独标记，不代替维护者估算 |

任何权重都必须写出理由，并做敏感性分析。权重不是“业务真理”，而是项目负责人公开声明的决策假设。

指标从 EDA 中发现的现象出发形成。每个核心指标记录：要支持的决定、字段来源、计算粒度、分母与时间窗口、缺失处理，以及可能误导判断的情况。例如，“重复性”可以检查某条规则在可比较且被观测到的快照中有多少次出现异常；缺失快照不能算作正常，也不能直接代表真实用户遇到问题的频率。最终选用哪些指标由数据检查决定。

先确定可比组、最低证据条件和缺失处理，再排序。大覆盖量是影响范围的代理，不能把它与严重程度等同；高证据质量也不能掩盖潜在但难核查的盲区。记录哪些候选因条件不明而无法比较，不强行给所有候选同一分数。

第一次排序分配的是**核查预算**。verify 之后的推荐才分配**后续测试或维护资源**。此时必须更新证据状态，不能照搬初始排名。

### 6.2 阶段二：Verify 候选问题

初步排序只代表“值得优先验证”，不代表问题已经被证明。

目标是对自定义排序的 **Top 10–20 个候选案例**逐项完成基础核查。先以 Top 10 安排工时，试跑确认可行后再增加到 20。

这里暂将“一个案例”理解为调查队列中的一个去重候选，有明确规则、环境、异常信号和可追溯样本。一条候选可能需要一个或多个网站来检查；10–20 个候选不等于 10–20 次运行，同一候选的重复运行也不增加案例数。第 2 周根据实际字段确定去重方式和样本映射。

每个入选案例都要实际尝试运行适用样本，并查看对应记录、保存结果；仅在表里排出 Top 20 不算完成核查。基础核查采用统一方案；其中对最终建议影响较大的少数案例可进一步重复运行或补充条件。一次观察只能支持当次结果，“反复失败”或“只在某条件下失败”需要额外证据。若样本不可访问或环境无法重建，保留该案例及未决原因，不悄悄换成容易成功的案例。

具体步骤是：

1. 选择少量代表性网站或测试样本；
2. 先定义预期行为与成功/失败条件，按预先确定的基础核查次数运行；需要判断重复性时再按约定补充运行；
3. 记录结果、错误阶段、截图和运行环境；
4. 检查历史记录和公开维护信息；
5. 将候选分类为：
   - 已复现：观察到符合预先定义的目标失败；
   - 条件性复现：只在明确条件下观察到；
   - 当前未复现：尝试后没观察到，历史真实性仍可能未知；
   - 已排除：证据表明候选来自解析错误、重复计数或其他已识别误解；
   - 无法判断：页面访问、环境或证据不足，无法完成有效检验。

“已修复”需要修复记录与匹配复测证据，另列为 follow-up 状态。当前未复现、issue 已关闭，都不足以单独证明曾经是误报或现在已修复。

核查使用干净的浏览器状态，并保存版本、日期、网络出口地区、语言和设备。浏览器语言或 `REGION` 标签不能替代真实地区环境。网页无法访问时记录为采集障碍，不计作 consent 失败。若无法重建英国等原环境，只报告当前环境观察，不称为原问题复现。

直接核验关键日志、页面状态或截图，避免仅用产生告警的同一个 self-test 来证明告警正确。弹窗关闭不自动说明选择已保存；本项目也不据此推断所有追踪活动停止。人工主要用于入选案例的证据判断和少量深查；运行、日志整理与结果汇总尽量批量化。试跑时同时记录人工耗时和自动运行耗时，不承诺完全自动化。

### 6.3 阶段三：形成行动建议

每个核查过的候选都要获得处置决定。只有证据达到门槛时才建议修复；证据不足时可以建议补充观测或暂缓，不能把它省略为“没有问题”。

根据问题的影响、证据质量、可复现性和成本，选择一项行动：

- 增加某类回归测试；
- 建立一组小型长期 benchmark；
- 提交带有复现步骤的公开 issue；
- 建议维护者优先修改某类规则；
- 增加某种失败监控；
- 如果证据不足，明确建议暂不投入。

项目必须给出“为什么是这个行动，而不是其他行动”的解释。

一条完整建议必须包含：决策对象、当前证据、推荐动作、负责角色、成本假设、验收办法、尚未解决的不确定性、最后验证日期。成本采用公开说明的情景估计；真实团队优先级仍需结合其内部约束。

### 6.4 阶段四：评估建议依据，再给最终推荐

默认闭环是：实现一套可复现筛选流程，核查候选，评价筛选依据，交付最终建议与证据。这里实际改变的是我们处理异常数据和形成建议的过程。工具修复和外部采纳是可选的进一步结果。

| 要评估的对象 | 方法与结果 | 可以声称什么 |
|---|---|---|
| 候选真实性 | 重复观察、独立证据核查 | 特定条件下已复现、排除或尚未判定 |
| 筛选方法 | 与简单基线做等预算比较，或合适的历史留出检验 | 在评估样本中是否提供额外价值 |
| 新增测试集 | 在有已知结果的案例上测检出情况 | 对这些案例的检出能力，不能代称工具成功率提升 |
| 实际执行的规则/配置改动（可选） | 对照测量差异 | 选定条件下工具表现变化；因果解释取决于设计 |
| 建议和证据包 | 完整性检查、可选的读者反馈 | 可追溯性与可理解性，不等于建议已被采纳 |

优先级方法的最小评估设计：

- 第 2 周选定一个简单基线，例如在相同可比规则组内按错误计数排序。它代表我们选的比较方案，不冒充 DuckDuckGo 内部流程。
- 固定候选池、预算口径和主要结果后再查看验证结果。预算可采用相同核查名额，另记录实际用时；有可靠成本数据才比较相同工时。
- 若做方法优劣比较，需要核查两种方法所选候选的并集，共同选中的只计一次，使用相同 protocol。不能只核查自己的 Top-K 就宣布优于基线。
- 两种方法使用同一个 K。自定义 Top 10 与基线 Top 10 最多需要核查 20 个不同候选；两边 Top 20 最多为 40 个。基线额外案例也计入工时，不能把它们藏在“核查 10–20 个”的估算里。先以 K=10 规划，是否扩大在核查前根据工时确定。
- 基础核查的结果用于公平比较；只对自定义首选进行的额外深查不能直接提高它在比较中的确认数。试跑中已经知道结果的案例标记为开发样本，不作为未见过结果的独立评价。
- 小样本只报告具体案例和“确认 x / 核查 y，未决 z”，并区分确认、可行动和严重性。预算不足以公平比较时，交付案例验证，不声称效率提升。

默认把“比简单排序多提供了什么”具体写成三类结果：选择了哪些不同候选；相同基础核查后各自确认、排除、未决多少；哪些新证据实际改变了建议及其原因。总用时用于说明实际成本。“有行动价值”的判断条件在核查前写清，不能事后把所有结果都算作收益。若两种方法选出同一批候选，就如实说明没有观察到选择上的增益。

历史回测仅在存在可比较的结果记录时启用：较早资料用于设计，冻结规则后使用后续资料评价；后来的 issue、PR 和结果不能回填过去的特征。重复 issue 和同一故障事件需去重。只有快照计数时，可以评价信号持续性，不能称为历史真实故障检出率。

最终建议根据评估维持、缩小、改为补证据或暂缓。尚未实际执行的动作附验收方案，状态保持“建议执行”。没有完成工具改动时不写“工具已改善”；没有外部使用记录时不写“业务已获益”。

### 6.5 Measurement 的解释边界

| 指标 | 使用条件 |
|---|---|
| 核查候选确认比例 | 写出分子分母和未决数；少量 Top-K 不能估计全体问题的误报率 |
| 已知案例检出情况 | 需要事先定义、独立核验的案例集合；没有完整真值不计算总体 recall |
| 排序稳定性 | 说明不同合理假设是否改变决策；稳定不代表正确 |
| 重复运行结果 | 分网站报告有效、失败和无法判断的次数；重复运行不是新增独立网站 |
| 工具效果差异 | 只针对实际执行的改动，见 §7.3；前后变化本身不证明因果 |

Top 10–20 是按优先级选择的案例，不是随机样本；候选还可能共享规则或网站。这个规模也不足以保证总体估计精确。数据不足时保留计数、差异和限制，不通过增加同一网站的运行次数制造“大样本”。

## 7. DS 技术要求

项目主体应体现以下 Data Science / Analytics 能力：

### 7.1 每个阶段使用的 skills

| 阶段 | 主要工作 | DS / Analytics skills | PM / 业务 skills | 主要证据 |
|---|---|---|---|---|
| 定义问题 | 明确谁要做什么决定 | problem framing、metric definition、假设拆解 | 识别决策者、目标和约束 | decision question |
| 理解数据 | 追踪数据如何生成并连接来源 | SQL、数据建模、data lineage、data quality | 判断数据能否支持业务结论 | source inventory、数据字典、可重建分析表 |
| 生成候选 | 从运行记录中找信号 | EDA、aggregation、rate/denominator、segmentation | 定义影响范围的合理代理 | candidate findings table |
| Verify | 判断候选是否为真 | repeated measurement、experiment design、error analysis、uncertainty | 设定证据门槛，避免误报 | verification evidence pack |
| 优先级 | 核查前选择候选，核查后提出处置 | 多指标比较、敏感性分析、简单基线比较 | trade-off、预算、证据门槛 | 调查队列和最终处置表 |
| 行动 | 将 finding 映射到下一步 | action-to-metric mapping、evaluation design | 维护任务、测试计划、issue 或反馈 | decision memo |
| 评价 | 检查建议依据与实际执行结果 | 样本偏差分析、留出评价（数据允许时）、受控实验（可选） | 维持、缩小或撤回建议 | evaluation result |
| 公开交付 | 让别人理解并复用 | reproducibility、documentation、result communication | audience design、责任披露、边界管理 | open-source site、case brief |

### 7.2 SQL 与本地 analytical warehouse

为了连接历史快照、核查记录和推荐依据，默认用 SQL 建立轻量级本地分析存储层：

- 使用 DuckDB 或 SQLite，不搭建云端生产数据仓库；
- 将原始 coverage、历史快照、GitHub 事件、运行结果和 finding 记录分层保存；
- 用 SQL 完成核心聚合、连接、去重、时间比较和候选生成；
- 保留 raw、cleaned 和 analytical tables 的关系；
- 为关键表增加基本的 schema、唯一性和完整性检查；
- 让网站和 notebook 使用同一份可重建的分析表。

关键建模要求是：聚合 coverage 事实表与逐次运行事实表保持不同粒度，通过明确的候选 ID 和证据链接关联，避免多对多连接放大计数。保留快照/来源版本、缺失值、自测是否适用，以及规则重命名映射。采用 CTE、JOIN、窗口函数完成有实际用途的历史比较；表名和数量在数据审查后确定。

这部分训练数据建模、ETL/ELT、SQL 查询和质量检查。分层采用最少必要结构；若单一文件已足够，则简化仓库设计，不引入无用云服务或复杂工具链。面试中准确称为“本地分析数据层”，不声称生产级数据仓库经验。

可以自然练习的较深入 SQL 问题包括以下几种，按数据条件选用：

| 要回答的分析问题 | 可用 SQL 方法 | 判断重点 |
|---|---|---|
| 某规则在相邻可比快照中出现了什么变化？ | `LAG`、按规则和地区分区的窗口计算 | 缺失时间点、规则版本变化不能误当成恶化或改善 |
| 哪些异常持续存在，哪些只有一次？ | CTE、条件聚合、滚动窗口 | 分母仅包含有效观测；缺失不补为零 |
| 某个排序时点之前已知哪些维护证据？ | 带时间条件的 JOIN、去重与 `ROW_NUMBER` | 后来的 issue 或修复信息不能泄漏到当时的指标 |
| 两种方法选中了谁，核查后有何不同？ | 排名窗口、集合连接、按状态聚合 | 候选去重、相同 K 和基础核查深度、未决结果保留 |

代码复杂度不是成果指标。成果是能解释查询为何这样写，识别连接导致的重复计数，并从原始资料重建支持建议的表。

### 7.3 Controlled experiment 与因果推断

A/B test 是支持因果推断的一种随机对照设计；因果推断并不等于 A/B test，也不要求结果必须是收入。我们可以研究工具结果，但当前没有真实用户流量实验的条件。

只有以下条件同时满足，才在主线完成后加入一个小型工具实验：问题已核实；存在与建议直接相关、可低成本执行的 Control/Treatment；结果可可靠测量；能安排可信比较且总投入不超过 50 小时。不能为了制造 Treatment 而额外接下复杂修复。

启用时预先写出实验方案：

1. 明确“哪项变化对哪个结果的影响”（estimand）、主要指标、样本选择、运行次数和停止条件；先检查样本规模能否提供有用精度，不承诺显著结果。
2. 选定网站、地区、设备和时段作为配对条件，随机化两版本的执行顺序，使用独立干净浏览器上下文，防止前一次 consent 状态污染后一次。
3. 除 Treatment 外固定可控配置；保存分配记录、版本、网络情况和所有失败运行，提前规定无效运行的处理方式。
4. 分网站报告差异。重复运行属于同一网站下的观测，不按独立网站计算精度；推断方法必须匹配配对和相关结构。样本太少时报告描述性差异，保留不确定性。
5. 区分处理完成、自测通过与其他目标结果；速度指标只有实际采集且完成质量没有下降时才有解释价值。

分组控制和随机化的设计依据见 [NIST 随机区组设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)。结论限定为所选环境的工具效果。简单前后比较、两种排序的离线比较，都不自动构成因果实验。

未启用时，记录原因并使用 §6.4 的默认评价路径。未开展因果实验不影响项目完成；只在实际完成时才写入技能成果。

### 7.4 数据理解与工程

- 识别不同数据源的生成过程；
- 建立 data dictionary 和 provenance；
- 读取和合并 coverage JSON、历史快照、测试元数据和 issue/PR；
- 处理 schema 变化、缺失字段、重复记录和不可比的分母；
- 保留原始数据与清洗后数据的关系。

### 7.5 分析与建模

- 选择合理的分析粒度；
- 区分数量、比例和分母；
- 进行 failure-mode segmentation；
- 分析时间趋势、重复出现和修复后的变化；
- 识别误报、选择偏差和可比性问题；
- 构建透明的多指标优先级框架；
- 做敏感性分析和不确定性说明；
- 用历史数据进行 backtesting（仅在结果记录和时间切分支持时）。

### 7.6 决策与评估

- 把候选问题转成可验证假设；
- 设计低成本、可复现的验证方案；
- 将 finding 映射到具体 action；
- 为 action 定义验收指标；
- 清楚说明 observation、interpretation 和 claim 的边界。

AI 可以辅助文本提取、初步分类、代码生成和假设挑战，但不能替代证据核验，也不能自动宣布某个网站违法。

### 7.7 能获得、部分获得和无法获得的能力

#### 本项目可以较强地展示

- 从模糊问题出发建立分析框架；
- 处理分散、不完整、带噪声的公开数据；
- 设计指标、分析粒度和数据质量检查；
- 识别候选信号并验证真假；
- 使用敏感性分析、基线或案例评价支持决策；历史回测取决于可用数据；
- 把数据分析转换成资源优先级和行动建议；
- 用可复现代码、证据链和清楚的限制进行沟通。

这些能力在 Data Analyst、Product Analyst、Decision Science、Privacy Analytics 和 Data Governance 等岗位中具有较强通用性。

#### 自然融入与条件增强

- **SQL / 数据仓库概念：**用于解决真实连接和历史比较问题；具体工具和层次保持轻量；
- **统计判断：**必须说明分母、样本选择、未决结果和相关性；区间估计只在设计和数据支持时使用；
- **实验与因果推断：**按 §7.3 条件启用；未完成则不声称掌握了实战 A/B；
- **stakeholder feedback：**可选，获得实际反馈才说明有需求验证；发送请求前由负责人确认。

#### 本项目不能替代真实 internship

- 真实用户流量 A/B test，以及具有商业 KPI 的完整因果推断；
- 生产级数据仓库、实时 pipeline 和大规模云基础设施；
- 真实收入、转化、客户流失或 ROI；
- 与法务、营销、工程和产品团队的长期协作；
- 真实组织是否采纳建议；
- 高级机器学习模型、模型部署和线上监控。

因此，面试时应说“完成了一次端到端的公开数据决策分析”，而不是声称做过生产级 DS 或证明了商业 ROI。

## 8. PM 与业务落点

项目负责人以 DS 身份把分析交给模拟的 PM／项目组。建议中要让接收者看懂：出现了什么现象、最有证据的解释是什么、还有什么不知道、下一轮可以如何分配调查或测试资源。

每个重要 insight 用“观察 → 可能解释与其他解释 → 证据 → 对决策的影响”记录。例如，若某候选的异常计数增加，先检查是否只是被检测到的网站数增加、规则或自测发生变化，再讨论是否值得优先查；这个例子仅说明分析思路，不是已有发现。无法确定根因时给出解释边界及补证据方案。

具体落点是：

1. 明确谁需要使用结果；
2. 明确他们要做什么资源分配决定；
3. 说明不同选项的 trade-off；
4. 给出推荐行动和验收标准；
5. 分开记录建议是否执行、候选是否可判断，以及实际执行后是否改善。

最终业务产出应类似一份内部 decision memo，以下仅为格式示例，不代表已有发现：

> 在当前证据和预算假设下，建议对 A 增加回归测试，对 B 补充观测。A 在指定条件下已复现，B 当前证据不足；这不表示 B 较轻或不存在。列明测试或观测的具体范围、成本假设、验收指标，以及哪些新增证据会改变建议。

这类建议希望带来的运营价值包括：

- 减少人工排查范围；
- 缩短从运行异常到维护决定的时间；
- 让测试和维护资源更集中；
- 提供可审查、可复现的决策依据；
- 降低因为 consent automation 不稳定而产生的维护不确定性。

本项目不能仅凭公开数据声称带来了具体收入、合规认证或真实用户数量的变化。若要增强业务真实性，可以在后期邀请一位开源维护者或隐私从业者对 decision memo 提供反馈。

明确区分三层成果：样本中的分析与评价结果；他人理解或采纳建议的记录；实际维护效果。只有第一层是本项目可自主控制的基本交付。其他层需要对应证据，不能从“写完建议”推导出“已节省人力”。

### 8.1 开源网站作为最终交付

项目可以沉淀成一个轻量级、静态的开源网站。网站是分析方法和结果的产品化呈现，不是另一个 CMP 或实时扫描平台。

最小网站可用一个页面分区呈现：

1. **Priority queue：**展示候选问题、verify 状态、影响范围代理、证据质量和推荐行动；
2. **Finding detail：**说明问题如何产生、使用了什么数据、如何复现、哪些结论仍不确定；
3. **Evaluation：**展示核查结果、与基线的比较或案例检验；时间趋势只在数据可比时展示；
4. **Method and limitations：**解释指标、权重、measurement、A/B 边界和数据限制；
5. **Download：**链接到已生成的 memo、数据和证据包，不另外开发在线生成系统。

网站不应只显示“哪些地方有问题”，而应回答：

> 基于目前证据，下一步最值得做什么？为什么？如果做了，应该如何判断是否有效？

第一版不做实时后台、用户账号、持续全网扫描或企业私有数据 connector。可以使用静态生成、GitHub Pages 或同类方式，避免把时间花在产品基础设施上。

每条建议显示证据状态、适用环境、最后核查日期和“建议/已执行/已评估”状态。网站展示的是某次版本化分析，不能让读者误以为所有问题现在仍存在或正在实时监测。方法可复用性尚未验证时也要明确标注。

## 9. 最小可行范围

十周内只做一个小闭环。以下是预算上限或起始假设，不是已经选定的样本：

- 一个主要问题族；
- 一个主要开源项目：AutoConsent；
- 一组有限的历史数据和公开维护记录；
- 自定义排序的 Top 10–20 个去重候选逐项基础核查，先以 10 个为执行起点；
- 同 K 的简单基线比较，额外候选也纳入基础核查和工时；少数候选再按决策需要深查；
- 实际网站数、运行次数与可支持的环境由试跑决定，单独记录，不与候选数混用；
- 至少一个有核查记录的最终处置，可以是建议行动、排除或仍无法判断，不要求一定发现 bug；
- 一次有实际结果的筛选评价：优先等预算基线比较；数据不足时做有明确限制的案例检验；
- 一个最小静态展示页与同源分析文件。

“可核查案例”不等于“统计代表性样本”。小闭环证明的是分析如何改变下一步决定，不预先承诺一定改善 AutoConsent 本身，也不以编写修复代码作为毕业条件。

以下内容不属于第一版：

- 全网大规模审计；
- 给网站或公司做法律合规排名；
- 训练预测模型；
- 建立大规模人工标注集；
- 开发新的浏览器自动化平台；
- 构建实时 SaaS、带后端的企业 dashboard 或持续全网扫描服务；
- 做真实用户流量 A/B test；
- 证明上游一定采用建议。

允许的最终展示形式是基于版本化分析结果生成的轻量级静态开源网站。

## 10. 十周工作计划与工作量

以下按项目负责人实际投入计，包括和 AI 讨论、阅读、操作、抽查、排错与整理，不把 AI 生成或脚本运行视为没有检查成本。基准计划 46 小时，平均每周 4–5 小时；其中同步讨论可以为 2–3 小时，其余用于操作和复盘。Top 10–20 扩大了核查范围，因此从原计划的可选增强额度中调配时间。50 小时是上限。

| 周次 | 工作内容 | 预计小时 | 产出 |
|---|---|---:|---|
| 1 | 检查需求假设、实际数据文件与历史记录；试跑一个样本，尽早暴露环境障碍 | 4 | 来源清单、试跑记录、可行性缺口 |
| 2 | 确认分析单位、来源和评价口径；根据试跑耗时估算 Top 10 加基线核查是否可行 | 4 | 数据字典、数据模型草图、核查工时估算与范围决定 |
| 3 | 最小数据提取、SQL 清洗连接与质量检查 | 5 | 可重建分析表和检查脚本 |
| 4 | EDA、缺失、分母和跨时间可比性检查 | 4 | 质量记录与异常分组 |
| 5 | 从 EDA 提炼指标、记录口径和解释，形成可重新运行的排序 | 4 | 指标定义与候选调查队列 |
| 6 | 敏感性分析；冻结核查样本、预算和 protocol | 4 | 基线对照方案与核查计划 |
| 7 | 按冻结方案核查 Top 10–20 与同 K 基线的并集，记录全部结果 | 7 | 运行证据、基础核查状态、实际耗时 |
| 8 | 完成剩余核查、必要深查与结果比较，解释证据如何改变决定 | 6 | 评价结果与面向 PM／维护者的初步建议 |
| 9 | 完成最终建议、验收方案与可复用方法说明 | 4 | decision memo、METHOD 初稿 |
| 10 | 同源结果生成最小静态展示页，检查复现流程，整理项目叙事 | 4 | 开源交付与总结 |

合计：核心 46 小时、排错缓冲 4 小时，总计不超过 50 小时。新增的 4 小时优先用于核查与评价，不再预留独立的 A/B 实验额度。可选实验只有在核心任务完成、仍有余量且满足 §7.3 时考虑。

第 2 周用试跑估计每个候选需要的人工时间，再把基线额外样本、环境搭建、必要重复和总结算进去。Top 20 是否可行不能仅凭“脚本可以自动跑”决定；默认完成 Top 10，工时允许再在第 6 周冻结前扩到 20。若连 Top 10 和必要评价都无法在上限内完成，明确列出缺口并与负责人重新定范围，不直接把目标改回只查 3 个。

若实际只能投入约 30 小时，应在第 2 周重新估算 Top 10 核查与比较，优先缩减来源、历史跨度和展示形式；核查目标仍超预算时再讨论范围。不能看到结果后随意减少重复次数或停止运行；预算不够时透明降低结论强度。持续跟踪实际工时，优先取消可选实验和界面美化。

## 11. 成功标准

项目完成不以数据量或图表数量衡量，而以以下结果衡量：

1. 能从公开原始数据重现主要分析结果；
2. 能清楚说明候选问题与已确认问题的区别；
3. 对约定的 Top 10–20 全部留下核查记录与处置；未完成或受阻的项目及原因公开列出，不算作已经有效验证；基线额外样本同样留痕；
4. 能解释最终优先级不是由单一数字决定；
5. 能给出一项具体处置及改变该建议的条件；证据不足时允许建议补观测或暂缓；
6. 有实际的筛选评价结果，而不只有未来计划；公平比较做不成时，只报告案例检验，不声称方法优于基线；
7. 能清楚说明数据限制、外推边界和未解决问题；
8. 核心候选生成和聚合能够用 SQL 在本地 analytical warehouse 中重建；
9. 清楚区分已实现的分析流程、建议行动与真实维护效果；工具实验仅在 §7.3 闸门通过后作为附加成果；
10. 另一个读者能够根据网站和方法文档复现主要判断；
11. 项目负责人能亲自解释关键 SQL、指标假设、一次判断的变化和未能得到的结论，不能只展示 AI 生成的产物。
12. 排序逻辑、参数、缺失处理和输入格式有文档；读者可以对同一输入重新生成调查队列，并沿证据理解建议。适配新来源需要什么也应说明。

“没有证实 bug”“未优于简单基线”“证据不足以推荐修复”都可以是有效结果，但必须有实际分析和核查支撑。只写框架、没有跑通数据和评价，不算完成。商业收益、上游采纳和统计显著改善均不是保证项。

## 12. 风险与转向条件

### 风险一：数据或运行环境不支持核查

第 1 周同时检查原始文件、示例网站映射、历史可比性和最小试跑。第 2 周结束前明确能支持的候选粒度与评价。若历史真值不足，取消历史检出率；若不能重建原地区，缩小到当前环境，不冒称原问题复现。

如果连一个候选的有效核查都无法完成，应停止当前实施计划，向负责人说明缺口，再讨论 issue/PR 等替代来源。替代来源也要重新检查可用性和结论边界，不能把自动换数据源当作已解决问题。

### 风险二：候选问题无法复现

这不是自动的失败或误报。按 §6.2 区分“当前未复现”“已排除”“无法判断”，保留环境差异和历史真实性的未知。不能为了得到正面故事而反复挑选直到命中。

### 风险三：项目逐渐变成代码修复

代码修改只能作为可选的小型试点。第 7 周后检查实验是否满足 §7.3；若需要复杂修复、额外地区基础设施或超过剩余工时，回到默认筛选评价和决策建议。数据准备与案例核查本身仍需动手，不能承诺完全无人操作。

### 风险四：没有外部组织采纳建议

项目应把“可复现 evidence package、实际评价和 decision memo”作为主要交付，外部 merge、部署或回应作为 stretch outcome。没有使用记录就保持为面向维护者的研究原型，不编写节省工时或商业 ROI。

### 风险五：公开证据包含敏感信息或再分发限制

记录来源与许可证。日志、截图和导出数据在发布前移除会话标识、账号信息等敏感内容；不采集真实个人账户、付款或登录后业务流程。不能公开的材料只提供可公开的引用和方法，不为复现而上传凭据。向上游发 issue、PR 或反馈请求前，另行由项目负责人确认。

## 13. 预期最终交付

最小开源交付包括以下内容，可以合并在同一组文件和网页中，不要求分别写十份长文：

1. data_dictionary.md；
2. 可复现的数据提取和分析代码；
3. 候选问题与优先级表；
4. verify 证据包；
5. 一份面向维护者的 decision memo；
6. 一份消费者或非技术读者能理解的 case brief；
7. 一份实际筛选评价结果；如果额外执行了行动，再附其 follow-up；
8. 一份方法论文档（METHOD.md）和可复用模板；
9. 一个基于分析结果生成的轻量级静态开源网站；
10. 一段诚实、可量化的简历描述。

### 方法论沉淀

最终沉淀的不是一套只适用于 AutoConsent 的打分公式，而是一套可迁移的 Evidence-to-Action workflow：

~~~
定义决策问题
→ 建立证据链
→ 生成候选
→ 分配核查预算
→ 核查并保留未决状态
→ 更新判断与选择行动
→ 评价筛选；实际执行行动时再测量效果
→ 公开限制并允许复用
~~~

方法文档必须写清楚输入、分析单位、候选生成规则、verify protocol、优先级维度、action-to-metric mapping、转向条件和不确定性说明。

复用的具体形式是：版本化 SQL／分析代码、可修改的排序参数、输入数据约定、核查记录模板与建议模板。网站展示同一套流程产出的结果；至少验证同一输入能重新生成一致的分析表和队列。对新快照或新项目的适用性需要额外检验，不能由“代码开源”直接推出。

在只有一个案例时，应称为“在一个案例中实践的可复用决策框架”，不应声称已经证明对所有 consent 或隐私问题普遍有效。跨问题族迁移测试留待下一阶段，不占用本次核心预算。

推荐的最终案例名称：

> **Consent Reliability Triage：从 AutoConsent 公开异常到有证据的维护建议**

## 14. 面试叙事模板

面试时应按以下顺序讲：

1. 业务背景：以 consent automation 为案例，研究有限调查预算下的维护决策；这是本项目设定的约束，不冒充 DuckDuckGo 内部需求；
2. 决策问题：有限时间下，下一轮应该先调查什么；
3. 数据问题：公开数据分散、字段不完整、候选失败尚未确证；
4. DS 方法：用 SQL 建立分析表、定义口径、核查候选、做敏感性与基线或案例评价；
5. 行动：根据核查证据决定测试、维护、补充观测或暂缓；
6. 结果：报告实际候选数、核查状态、比较结果和建议变化；只有执行了改动才报告改动效果；
7. 限制：没有企业内部流量和商业结果，因此只报告能够被公开证据支持的结论。

不要把项目说成已经替代企业内部审计，也不要把工具层失败直接说成法律违规。

## 15. 已定方向与后续决策

已定方向：模拟分析型 DS 从 messy data 提炼指标与 insight、支持 PM／项目组决策；以开源第三方视角开展；AutoConsent 为首个案例；保留轻量 SQL 数据层与可复用排序流程；核查自定义 Top 10–20 并与简单基线比较；可选实验不得破坏主线；30–50 小时封顶。

以下内容不提前编定：

- **第 1–2 周决定：**具体来源与时间窗口、可比较问题族、候选如何计数、能运行的环境、结果证据、基线与工时估算；若不支持 Top 10 的闭环，先讨论范围调整。
- **第 6 周核查前冻结：**K 在 10–20 中取多少、两种方法的候选并集与样本、有效/失败/未决条件、基础与深查次数、停止规则和最终评价指标；后续变更单独记录。
- **第 7 周后决定：**是否存在值得执行的小型 Treatment；默认不修改规则、不开展因果实验。
- **对外沟通前决定：**是否发上游 issue/PR、邀请反馈。发布到本项目自己的 GitHub 仓库不等于获得这些对外沟通的授权。

每次重要决定记录日期、选项、依据、舍弃理由与重开条件。后续更新这个文件即可；无需为了计划完整而预先虚构实验结果、业务需求或数据能力。
